# 1. Creational Design Patterns

```text
Create a reusable Codex skill named:

nodejs-creational-design-patterns

Install it as a repository-local Codex skill under:

.codex/skills/nodejs-creational-design-patterns/

The skill should teach Codex how to recognize, select, implement, refactor, and review creational design patterns in production Node.js and TypeScript applications.

PRIMARY SOURCE

Base the skill on the concepts from Chapter 7, "Creational Design Patterns", of:

Node.js Design Patterns, Fourth Edition
Luciano Mammino and Mario Casciaro
Packt Publishing, 2025

Also inspect the corresponding examples in the official PacktPublishing/Node.js-Design-Patterns-Fourth-Edition repository.

Do not reproduce copyrighted prose from the book. Extract engineering principles, decision criteria, implementation techniques, pitfalls, and patterns in your own words. Code examples created for the skill must be original.

COVERAGE

The skill must cover:

1. Factory
   - decoupling object creation from implementation
   - runtime implementation selection
   - encapsulation through factories and closures
   - factory functions versus constructors/classes
   - dependency injection through factories

2. Builder
   - incremental construction of complex objects
   - fluent APIs
   - validation
   - immutable final products
   - when builders improve readability versus when they create unnecessary abstraction

3. Revealing Constructor
   - controlled mutation during initialization
   - exposing a restricted capability to initialization code
   - immutable objects after construction
   - security and encapsulation implications

4. Singleton
   - module-based singleton behavior in Node.js
   - ESM module caching
   - singleton dependencies
   - lifecycle and global-state risks
   - testing problems introduced by singletons
   - situations where dependency injection is preferable

5. Wiring modules and Dependency Injection
   - composition roots
   - explicit dependency wiring
   - constructor/factory injection
   - testability
   - avoiding service-locator style hidden dependencies

SKILL BEHAVIOR

The skill should activate when Codex is asked to:

- create objects whose implementation varies
- improve dependency construction
- introduce factories or builders
- remove hard-coded dependencies
- review singleton usage
- improve object initialization
- refactor constructors
- design dependency injection
- choose an appropriate creational pattern

It should NOT automatically recommend a design pattern merely because one exists.

Require Codex to first determine:

- What problem exists?
- Is object creation actually complex?
- Does the implementation need runtime selection?
- Does the object require staged construction?
- Is controlled initialization required?
- Does state genuinely need process-wide uniqueness?
- Would ordinary functions or direct construction be simpler?

Favor the simplest implementation that satisfies the requirement.

Create:

SKILL.md
references/pattern-selection.md
references/typescript-examples.md

SKILL.md MUST contain:

- YAML frontmatter with name and precise activation description
- When to use
- When NOT to use
- Inputs/context to inspect
- Pattern-selection workflow
- Refactoring workflow
- Implementation workflow
- JavaScript/TypeScript considerations
- Testability requirements
- Common anti-patterns
- Verification checklist

Create a concise decision table in references/pattern-selection.md comparing:

Factory
Builder
Revealing Constructor
Singleton
Dependency Injection
Direct construction/no pattern

For every pattern describe:

Problem
Signals
Benefits
Costs
Testing implications
When not to use it

Use modern ESM and Node.js 24+ conventions.

Do not introduce dependencies when native JavaScript/Node.js is sufficient.

Make this a practical coding skill, not a design-pattern tutorial.
```

   - bounded concurrency
   - worker pools

SKILL.md

I/O-bound
CPU-bound
memory-bound

Do NOT introduce worker threads merely because an operation is asynchronous.

Use a decision sequence roughly equivalent to:

Small CPU task -> keep simple
Long task where responsiveness alone matters -> consider chunking/yielding
CPU parallelism inside Node process -> worker threads
Strong isolation or separate executable/runtime -> external process
Repeated CPU jobs -> bounded worker pool

Require verification of:

event-loop responsiveness
throughput
latency
CPU utilization
memory
worker count
queue depth
failure behavior

Warn against:

one worker per request
unbounded concurrency
expensive serialization
blocking the main thread while waiting
worker/resource leaks
assuming more workers always improve throughput
running significantly more workers than available CPU without evidence

Require benchmarks or load tests before claiming an optimization.

Use Node.js 24+, ESM, and modern TypeScript where appropriate.
