# Codex Skill Creation Prompts — Node.js Design Patterns, 4th Edition

## 1. Creational Design Patterns

Create a Codex Agent Skill named:

`nodejs-creational-design-patterns`

Use the built-in `$skill-creator` skill if available.

Create the skill in the normal Codex skills directory:
`${CODEX_HOME:-$HOME/.codex}/skills/nodejs-creational-design-patterns`

The skill should operationalize the concepts from Chapter 7, **Creational Design Patterns**, of *Node.js Design Patterns, Fourth Edition* by Mario Casciaro and Luciano Mammino.

Use the official public example repository as a reference:
`https://github.com/PacktPublishing/Node.js-Design-Patterns-Fourth-Edition/tree/main/07-creational-design-patterns`

Do not reproduce copyrighted book prose. Derive practical engineering guidance from the concepts and public examples.

The skill must help Codex inspect an existing Node.js/TypeScript/JavaScript codebase and determine whether any of these techniques are appropriate:

* Factory
* Builder
* Revealing Constructor
* Singleton
* dependency injection
* module wiring/composition

The skill must explicitly teach Codex to distinguish between:

* a real need for a creation pattern and unnecessary abstraction;
* Factory versus direct construction;
* Builder versus simple object/configuration construction;
* Singleton versus module caching versus dependency injection;
* object creation and dependency wiring.

The skill should follow this workflow:

1. Inspect the existing code and architecture.
2. Identify the construction/configuration problem.
3. Determine whether a creational pattern is actually justified.
4. Select the simplest suitable pattern.
5. Explain the decision briefly.
6. Implement or refactor the code.
7. Preserve existing public APIs unless changing them is necessary.
8. Add or update tests.
9. Run the project's available tests, linting, type checking, and formatting.
10. Report what changed and the tradeoffs.

Prefer:

* modern ESM;
* Node.js 24+;
* TypeScript when the repository already uses TypeScript;
* explicit dependency injection;
* small composable modules;
* testable designs.

Avoid:

* pattern-for-pattern's-sake implementations;
* global mutable singletons;
* service locator anti-patterns;
* unnecessary classes where functions or object composition are simpler.

Create:

* `SKILL.md`
* `agents/openai.yaml`
* `references/pattern-selection.md`
* `references/examples.md`

Keep `SKILL.md` concise and move detailed examples and pattern comparisons into `references/`.

Include realistic original examples rather than copying the book.

The skill description must make Codex automatically consider this skill when the user asks to design, refactor, review, or choose object creation, dependency construction, configuration builders, factories, singletons, dependency injection, or module wiring in Node.js.

Validate the completed skill before finishing.

## 2. Structural Design Patterns

Create a Codex Agent Skill named:

`nodejs-structural-design-patterns`

Use `$skill-creator` if available.

Install it under:
`${CODEX_HOME:-$HOME/.codex}/skills/nodejs-structural-design-patterns`

Base the engineering knowledge on Chapter 8, **Structural Design Patterns**, of *Node.js Design Patterns, Fourth Edition*.

Public reference implementation:
`https://github.com/PacktPublishing/Node.js-Design-Patterns-Fourth-Edition/tree/main/08-structural-design-patterns`

Do not reproduce the book text.

The skill should make Codex proficient at identifying, implementing, reviewing, and refactoring:

* Proxy
* JavaScript `Proxy`
* Decorator
* object augmentation
* Adapter
* composition-based wrappers

A critical responsibility of the skill is distinguishing:

* Proxy: controls or mediates access while preserving the underlying contract.
* Decorator: adds responsibilities or behavior while preserving compatibility.
* Adapter: translates one interface into another expected by the consumer.

The skill must make Codex inspect the code before recommending a pattern.

Workflow:

1. Identify the incompatible, cross-cutting, or behavior-extension problem.
2. Inspect existing interfaces and callers.
3. Determine whether Proxy, Decorator, Adapter, ordinary composition, or no pattern is appropriate.
4. Preserve interface compatibility wherever practical.
5. Implement the smallest solution.
6. Avoid inheritance where composition is simpler.
7. Add tests covering delegation and edge cases.
8. Run type checking, tests, linting, and formatting.
9. Explain the structural tradeoff briefly.

Include production-oriented guidance for common Node.js cases such as:

* logging;
* metrics;
* caching;
* authorization wrappers;
* retry wrappers;
* API/client adapters;
* stream wrappers;
* compatibility layers around third-party libraries.

Do not automatically introduce a Proxy or Decorator for simple utility functions.

Create:

* `SKILL.md`
* `agents/openai.yaml`
* `references/proxy-vs-decorator-vs-adapter.md`
* `references/examples.md`

The skill must be action-oriented and usable during actual implementation and code review, not merely as a design-pattern tutorial.

## 3. Behavioral Design Patterns

Create a Codex Agent Skill named:

`nodejs-behavioral-design-patterns`

Use `$skill-creator` if available and place it in the normal Codex skills directory.

Base it on Chapter 9, **Behavioral Design Patterns**, of *Node.js Design Patterns, Fourth Edition*.

Official public examples:
`https://github.com/PacktPublishing/Node.js-Design-Patterns-Fourth-Edition/tree/main/09-behavioral-design-patterns`

Cover:

* Strategy
* State
* Template
* Iterator
* iterable protocol
* async iterators
* async generators
* Middleware
* Command

The skill should allow Codex to recognize behavioral complexity in real Node.js code and choose the appropriate mechanism.

Teach Codex to distinguish:

* Strategy for interchangeable algorithms.
* State for behavior that depends on explicit lifecycle/state transitions.
* Template for a stable algorithm skeleton with variable steps.
* Iterator/async iterator for controlled traversal or asynchronous sequences.
* Middleware for ordered processing pipelines.
* Command for representing an operation as data/object so it can be queued, retried, logged, stored, or executed later.

Workflow:

1. Inspect current control flow.
2. Identify what varies.
3. Determine whether a behavioral pattern simplifies that variation.
4. Prefer native JavaScript language features where they are sufficient.
5. Implement with minimal coupling.
6. Make state transitions explicit where applicable.
7. Preserve async error propagation and cancellation semantics.
8. Add tests for alternative strategies/states/commands and failure paths.
9. Run validation tools.

Include guidance for:

* async iteration over paginated APIs;
* streaming data;
* middleware pipelines;
* workflow/state machines;
* pluggable algorithms;
* retryable or serializable commands.

Create:

* `SKILL.md`
* `agents/openai.yaml`
* `references/pattern-selection.md`
* `references/async-iteration.md`
* `references/examples.md`

Do not turn simple `if` statements into State/Strategy objects without a meaningful maintenance benefit.

## 4. Testing: Patterns and Best Practices

Create a Codex Agent Skill named:

`nodejs-testing-patterns`

Use `$skill-creator`.

Target modern Node.js 24+ development.

Use Chapter 10, **Testing: Patterns and Best Practices**, of *Node.js Design Patterns, Fourth Edition* as the conceptual foundation.

Official examples:
`https://github.com/PacktPublishing/Node.js-Design-Patterns-Fourth-Edition/tree/main/10-testing`

The skill should guide Codex when creating, reviewing, fixing, or refactoring Node.js tests.

It must cover:

* Node.js built-in `node:test` runner;
* assertions;
* suites and subtests;
* asynchronous tests;
* concurrent tests;
* test coverage;
* TypeScript testing;
* unit testing;
* dependency injection for testability;
* mocking HTTP;
* mocking Node/core or external modules when justified;
* integration tests;
* HTTP integration tests;
* end-to-end tests.

The workflow must begin by identifying the appropriate test level.

Use this priority:

1. Unit tests for isolated business logic.
2. Integration tests for component boundaries where real interactions matter.
3. E2E tests only for high-value complete workflows.

The skill must discourage:

* excessive mocking;
* tests coupled to implementation details;
* duplicating the same scenario at every test level;
* flaky sleeps;
* global mutable fixtures;
* testing private implementation details rather than observable behavior.

Prefer:

* deterministic fixtures;
* dependency injection;
* clear Arrange/Act/Assert structure;
* isolated test data;
* explicit cleanup;
* meaningful failure messages;
* fast unit tests;
* realistic integration tests;
* minimal high-value E2E coverage.

When operating in an existing repository, preserve its existing testing framework unless there is a strong reason to change it.

Create:

* `SKILL.md`
* `agents/openai.yaml`
* `references/test-level-selection.md`
* `references/mocking-and-dependency-injection.md`
* `references/node-test-runner.md`
* `references/examples.md`

The skill should be capable of both implementing new tests and reviewing an existing test suite for design problems.

Always run the applicable tests and report failures rather than assuming correctness.

Public examples:
`https://github.com/PacktPublishing/Node.js-Design-Patterns-Fourth-Edition/tree/main/12-scalability-and-architectural-patterns`

The skill must help Codex reason about Node.js systems that need to scale beyond a single execution context.

Cover:

* vertical versus horizontal scaling;
* cloning application instances;
* Node.js multi-process execution;
* load balancing;
* process failure and restart;
* graceful shutdown;
* zero-downtime replacement;
* dynamic load balancing;
* peer-to-peer approaches;
* containerized scaling;
* Kubernetes scaling;
* decomposing complex applications;
* modular monolith versus services;
* distributed-system tradeoffs.

The skill must **not** recommend microservices automatically.

5. Determine whether vertical scaling, process cloning, containers, queues, caching, partitioning, or service decomposition is appropriate.
6. Preserve statelessness where horizontal scaling requires it.
7. Identify shared-state/session problems.
8. Address graceful shutdown/readiness/health behavior.
9. Add observability appropriate to the change.
10. Add or update tests.
11. Validate using existing performance or integration tooling when available.

The skill should explicitly warn about:

* distributed complexity;
* duplicated state;
* sticky-session dependencies;
* database bottlenecks hidden by application scaling;
* premature microservice decomposition;
* load balancing without health checking;
* unbounded queues.

## 10. Running CPU-Bound Tasks

Create a Codex Agent Skill named:

`nodejs-cpu-bound-work`

Use `$skill-creator`.

Base it on the **Running CPU-bound tasks** section of Chapter 11, Advanced Recipes.

Official examples:
`https://github.com/PacktPublishing/Node.js-Design-Patterns-Fourth-Edition/tree/main/11-advanced-recipes`

The skill must help Codex prevent CPU-intensive work from blocking the Node.js event loop.

Cover:

* recognizing CPU-bound workloads;
* event-loop blocking;
* `worker_threads`;
* worker lifecycle;
* worker pools;
* message passing;
* transferable data when appropriate;
* worker failure;
* worker cancellation;
* bounded concurrency;
* process isolation where appropriate;
* external job queues for workloads that should not execute in-process.

Workflow:

1. Inspect the workload.
2. Determine whether it is genuinely CPU-bound.
3. Measure or profile when practical.
4. Decide between:

   * direct event-loop execution;
   * `worker_threads`;
   * worker pool;
   * child process;
   * separate service/job worker.
5. Avoid creating an unbounded number of workers.
6. Define task timeout/cancellation.
7. Propagate worker errors.
8. Gracefully terminate workers.
9. Test success, failure, cancellation, and concurrency behavior.
10. Check event-loop responsiveness after implementation.

The skill must teach that asynchronous syntax does **not** make CPU-heavy JavaScript non-blocking.

Prefer the simplest mechanism that meets isolation, performance, and operational requirements.

Create:

* `SKILL.md`
* `agents/openai.yaml`
* `references/cpu-work-decision-guide.md`
* `references/worker-threads.md`
* `references/examples.md`
