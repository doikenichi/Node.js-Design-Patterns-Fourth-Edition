# Pattern Selection

Use this table to choose the simplest structural design that solves the actual problem. The pattern name should describe the role the wrapper plays for the rest of the system.

| Pattern | Problem | Signals | Benefits | Costs | Testing implications | When not to use it |
| --- | --- | --- | --- | --- | --- | --- |
| Direct function or ordinary composition | A small local operation needs a mapper, predicate, callback, or helper. | One call site, obvious transformation, no external contract, no lifecycle boundary, no need to hide a dependency. | Least indirection, easiest typing, clear stack traces, no wrapper lifecycle. | Can become duplicated if the need spreads. | Test through the calling behavior or the helper if it has branching. | The behavior must be reused around many implementations, protect a domain boundary, or preserve a stable contract during migration. |
| Proxy with explicit wrapper | Access to a subject must be controlled, validated, logged, delayed, observed, or forwarded behind the same basic surface. | Authorization checks before calls, validation before mutation, lazy resource creation, logging/metrics around method access, wanting to preserve subject API with some guarded operations. | Readable, type-friendly, debuggable, fast enough for most paths, clear place to handle `this`. | Forwarding can be repetitive; wide APIs are tedious; wrapper may drift from the subject. | Test guarded and forwarded methods, denied paths, error propagation, and `this` binding. | The wrapper is only adding a new capability rather than controlling access, or the surface is highly dynamic and explicit forwarding becomes fragile. |
| Proxy with JavaScript `Proxy` | Dynamic interception is the core requirement. | Unknown property names, observable object mutation, lazy method/property wrapping, virtual collections, broad forwarding, instrumentation across a large surface. | Minimal boilerplate for wide/dynamic APIs, can intercept get/set/has/apply/construct/delete operations, useful for observation and virtual behavior. | Runtime magic, weaker TypeScript precision, potential performance cost, recursive trap risks, harder debugging. | Test relevant traps, repeated access behavior, identity assumptions, method extraction, serialization, and performance-sensitive flows. | A few explicit methods would be clearer, the path is hot, or type safety/debuggability matter more than dynamic interception. |
| Decorator | A component should keep its role but gain extra behavior or capabilities through composition. | Add caching, metrics, logging, retry, compression, validation, methods, event publishing, or policy around an existing service without modifying it. | Open for extension without changing the wrapped component, composable, testable with fakes, avoids inheritance for optional behavior. | Order can matter; stacks can become hard to trace; transparent behavior changes surprise callers. | Test base behavior preservation, added behavior, ordering, error propagation, and cleanup/flush behavior. | The new behavior is a core invariant that belongs inside the component, or the wrapper mostly controls access rather than extends behavior. |
| Adapter | Consumers need a stable contract while an incompatible API sits behind it. | Third-party SDK names leak everywhere, legacy module signatures differ, migration from old provider to new provider, domain code knows infrastructure-specific errors/options. | Isolates infrastructure, preserves domain-facing contracts, supports provider migration, reduces test coupling to external libraries. | Mapping code can grow, incomplete contract coverage, error translation decisions need care, adapter can become too broad. | Test data mapping, option mapping, errors, unsupported provider features, pagination/streaming/cancellation semantics, and consumer independence from the adaptee. | The dependency already exposes exactly the domain contract or a local mapper at the boundary is enough. |

## Selection Notes

- Proxy and Decorator both wrap; choose based on intent. Proxy primarily controls access to a subject. Decorator primarily extends behavior while preserving the subject's role.
- Adapter is about interface translation, not just adding logging or validation.
- A wrapper around a third-party client is often both an Adapter and a place to apply Decorators. Keep those roles separate when the combined code becomes hard to reason about.
- Object augmentation is convenient but risky when the same instance is shared. Prefer composition when callers need the original and wrapped behavior to coexist.
- JavaScript `Proxy` is a technique, not automatically the Proxy pattern. A `Proxy` can implement Proxy, Decorator, Adapter-like dynamic translation, observability, or virtual objects.
- If the only purpose is logging one function call, start with a small higher-order function.
