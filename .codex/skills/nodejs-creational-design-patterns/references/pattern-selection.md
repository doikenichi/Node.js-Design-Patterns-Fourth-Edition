# Pattern Selection

Use this table to choose the simplest creation design that solves the actual problem. Avoid introducing a pattern when direct construction communicates the intent more clearly.

| Pattern | Problem | Signals | Benefits | Costs | Testing implications | When not to use it |
| --- | --- | --- | --- | --- | --- | --- |
| Factory | Call sites should not know how to construct or choose a concrete implementation. | Repeated `new` plus branching, selection by config/file type/protocol/env, private implementation details, need to inject dependencies during creation. | Centralizes creation, hides classes, supports runtime selection, enables closure-based encapsulation, gives consumers a stable capability. | Can hide side effects, can become a service locator, selection logic can grow messy, may obscure concrete lifecycle ownership. | Test mapping from inputs to behavior, unsupported variants, injected dependency flow, and error messages. Consumers can test against fakes. | Only one implementation, trivial construction, no repeated branching, or a plain helper/options object is clearer. |
| Builder | Construction has many optional or staged values and readability or validation suffers. | Long positional constructors, many optional params, invalid combinations, fluent domain language improves call sites, final product needs validation before use. | Improves construction readability, localizes validation/defaults, supports fluent APIs, can return immutable products. | Extra class/function layer, mutable intermediate state, overkill for simple data, chains can hide required values until runtime. | Test required fields, defaults, invalid combinations, chain order if relevant, and final object immutability. | An object literal with a typed options object is clear, there are few parameters, or the builder only mirrors property names. |
| Revealing Constructor | Initialization code needs temporary mutation rights, but the completed object should expose only safe operations. | A callback/executor should fill/write/register during construction; mutation methods must not be public later; capability should be narrower than the backing object. | Enforces capability boundaries, enables controlled setup, supports immutable public surface after construction. | Callback can be surprising, errors during construction need care, capability design must be tight, async executors are risky unless explicitly supported. | Test allowed initialization mutation, rejected/missing capabilities after construction, invalid executor errors, and final public API immutability. | A normal constructor/factory can validate inputs, mutation is safe after construction, or initialization requires broad long-lived privileges. |
| Singleton | One process-wide instance is a real invariant or resource owner. | Shared cache/config/registry/client must be unique per process; eager module export already provides correct lifecycle; duplicate instances would break correctness. | Simple access through ESM caching, avoids repeated expensive setup, useful for immutable config or process-level registries. | Global state, hidden coupling, difficult resets, import-time side effects, lifecycle ambiguity, false uniqueness across duplicate packages/processes/workers. | Tests need reset/isolation strategy, must avoid order dependence, should verify lifecycle and document scope. Prefer integration tests for real singleton wiring. | Most dependencies can be passed in; tests need independent instances; state varies per request/tenant; async startup/shutdown must be explicit; uniqueness across processes is required. |
| Dependency Injection | Business logic should depend on capabilities, not concrete modules or global instances. | Domain modules import databases/clients/loggers directly, tests mock modules, wiring is scattered, dependency choice varies by environment. | Improves testability, makes dependencies visible, separates construction from use, supports composition roots and replacement. | More plumbing, constructors/factories need parameters, overdone interfaces can add noise, manual wiring grows in large apps. | Unit tests pass small fakes/stubs; composition-root tests verify real wiring; fewer module mocks needed. | Tiny scripts with no test seam needs; dependency never varies; passing dependencies would make simple code harder to follow. |
| Direct construction/no pattern | Creation is obvious and stable. | Few required args, no runtime selection, no lifecycle ambiguity, no repeated construction ceremony. | Maximum readability, least indirection, best local reasoning, no extra API to maintain. | Duplication can appear later, call sites may absorb future branching. | Tests instantiate directly and assert behavior. | Creation rules become repeated, implementation varies, constructor args become fragile, initialization needs a boundary, or dependencies need replacement in tests. |

## Selection Notes

- Factory and Dependency Injection often work together: the composition root calls factories, then injects the created dependencies into business services.
- Builder is usually for readability and invariants, not for hiding implementations.
- Revealing Constructor is a capability-control pattern. Use it when the temporary mutation boundary matters.
- Singleton is a lifecycle decision, not just a convenience export.
- Direct construction should remain the default until there is a concrete reason to move creation behind a boundary.
